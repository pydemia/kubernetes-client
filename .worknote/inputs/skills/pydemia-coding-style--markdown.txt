Markdown

문서는 독자가 실행·검토·결정하는 데 필요한 내용으로 구성한다. 문장 표현은
DOC-003, 기술 설명과 변경 이력은 아래 항목을 함께 적용한다.

MD-001 — 79자 hard wrap과 보존해야 할 줄


상태: 명시

적용 범위: 일반 Markdown 본문

근거: L01


일반 문장은 79자를 기준으로 줄을 나눈다. URL·hash·식별자·표·그대로
실행해야 하는 명령은 의미를 깨며 분리하지 않는다. 소스의 줄바꿈과 렌더링된
문단·강제 줄바꿈을 구분한다.

이유: 개인 개발 지침이 일반 Markdown의 hard wrap과 예외를 명시한다.

예외·한계: 프롬프트·코드·표의 literal을 산문처럼 재배치하지 않는다. 기존 renderer의
동작이 필요한 경우 실제 화면을 확인한다.

MD-002 — 목록과 산문의 역할


상태: 명시

적용 범위: 설계·리뷰·사용 가이드·보고 문서

근거: 추가 대화 U27, L01


요약·비교·순서·검토 항목은 제목과 목록·표로 읽기 쉽게 작성한다. 조건과
이유를 연결해 설명해야 하면 산문을 사용한다. 정해진 항목 수로 내용을
억지로 나누거나 같은 요약을 여러 위치에 반복하지 않는다.

이유: 사용자가 읽기 어려운 줄글은 개조식으로 줄이되 상세 설명은 산문으로 남기도록
요청했다. 최신 공통 지침도 목적에 따른 형식을 우선한다.

예외·한계: 모든 문서를 개조식 또는 존댓말 완전문으로 강제하지 않는다. 산출물의 독자와
기존 문체를 보존한다.

MD-003 — 코드 예제와 근거 링크


상태: 선호

적용 범위: README·개발 가이드·리뷰·보고

근거: 추가 대화 U28


fence에는 실제 언어를 적고 예제의 placeholder와 실행 가능한 부분을
구분한다. 링크는 설명한 주장과 가까이 두고 코드 근거는 가능하면 revision과
행을 고정한다. 외부 공개 예제의 계정·저장소·주소는 익명화한다.

이유: 정확한 코드 참조를 보존하고 공개 예제의 실제 업무 저장소 이름을 바꾸도록
요청한 기록에 근거한다.

예외·한계: 현재 API를 설명하는 문서는 오래된 commit 예제가 현재와 같은지 확인한다.
근거를 고정하는 일과 최신 동작을 주장하는 일은 다르다.

MD-004 — 원본과 생성 문서의 구분


상태: 조건부

적용 범위: Skill hub·정의 파일·설계 문서·export

근거: 추가 대화 U23, L04


수정할 관리 원본과 생성 결과를 먼저 확인한다. 같은 정책을 여러 파일에
복사해 별도로 갱신하지 않는다. 공통 내용은 링크로 참조하고 exporter가
만드는 파일은 원본 수정 후 다시 생성한다.

이유: Skill hub와 업무 정의의 중복 제거 요청에서 관리 원본의 일관성을 확인했다.

예외·한계: 모든 Markdown을 생성물로 취급하지 않는다. 사이트별 frontmatter·디렉터리
규칙은 실제 프로젝트 가이드를 따른다.

MD-005 — 설계의 사실·가정·제안 구분


상태: 명시

적용 범위: architecture·구현계획·대안 비교·도식

근거: L01, 추가 대화 U29


확정 요구, 현재 동작, 제약, 가정, 제안과 선택 사항을 구분한다. 어느 구성
요소가 호출하고 상태를 저장하며 실패를 처리하는지 적는다. 대안은 실제
운영·보안·성능·마이그레이션 조건으로 비교한다. 도식에는 실제 필요한
구성 요소만 넣고 상호작용·분기·배치에 맞는 도식 종류를 선택한다.

이유: 개인 설계 지침에 명시되어 있으며 구조 변경의 이유를 architecture 문서에
누적해 달라는 직접 요청이 있다.

예외·한계: 설계 제안을 구현 완료로 표시하지 않는다. 예쁘게 보이기 위한 가상 계층이나
검증하지 않은 수치를 추가하지 않는다.

MD-006 — 최신 결정과 변경 이력


상태: 명시

적용 범위: 정책·설계·convention의 수정

근거: U30


동일 범위의 명시적 결정이 충돌하면 최신 결정을 적용한다. 과거 결정은 현재
규칙과 분리해 변경 이유와 함께 기록한다. A→B→A처럼 번복한 항목은 선택
순서, 각 이유, 현재 기준, 다시 결정할 쟁점을 별도로 제시한다.

이유: 이번 조사 중 사용자가 최신 기준의 우선과 반복 번복의 별도 정리를 직접
지시했다.

예외·한계: 파일 수정 시각만으로 사용자 결정 시각을 추정하지 않는다. 복제된 대화와
다른 프로젝트의 선택은 같은 정책의 번복으로 세지 않는다.

작성 예

변경 이유, 동작과 검증 범위를 연결해서 설명한다. 다음은 문장 구성 예제이며
실제 프로젝트에서 수행한 검증 결과가 아니다.

기존에는 조회 timeout을 빈 결과로 반환했다. 이제 timeout 오류를 보존해
호출자가 재시도 여부를 결정할 수 있게 했다.

- 정상적인 빈 결과는 기존 응답 형식을 유지한다.
- 회귀 테스트에서 timeout과 빈 결과가 구분되는 것을 확인했다.
- 실제 운영 DB의 네트워크 장애는 재현하지 않았다.
