DOC-001 — 함수 docstring과 이유를 설명하는 주석


상태: 명시

적용 범위: 코드 문서화

근거: U02 · U01 · L01
· G04


함수의 목적·입출력 조건·예외·비직관적 제약은 docstring에 둔다. 코드 한 줄마다 동작을 다시 설명하지 않는다. inline
comment는 분기 이유, 외부 제약, 호환성, 불변식처럼 코드만으로 알기 어려운 정보에 사용한다.

이유: 줄별 주석 대신 함수 docstring을 요청했고, 다른 설계 요청에서도 왜 필요한지를 남기도록 했다.

예외·한계: 모든 private 함수에 장문의 문서를 만들지 않는다. 공개 API와 복잡한 경계를 우선하고 변경된 동작에 맞춰 오래된
설명을 수정한다.

DOC-002 — docstring 형식


상태: 관측

적용 범위: 새 Python library의 공개 API

근거: G03 · G04 · G01


정해진 형식이 없는 새 library는 NumPy식 Parameters·Returns·Raises·Examples를 후보 기본값으로 삼는다.
필요한 항목만 작성하고 예제의 입력과 결과가 실제로 맞는지 확인한다.

이유: unipy의 docstring template와 IAM의 공개 Protocol에서 같은 계열의 형태를 확인했다. 개인의 절대
규칙으로 명시된 것은 아니다.

예외·한계: dynamic-batcher에는 Google식 Args·Returns도 있다. 기존 Google·Sphinx 형식을 이
규칙으로 전면 변경하지 않는다. 타입 annotation을 의미 없이 반복하지 않는다.

DOC-003 — 구체적인 한국어와 정확한 용어


상태: 명시

적용 범위: 개발 문서·보고·설계 설명

근거: U00 · L01 · L06


기본 프로젝트 문서는 한국어로 쓰되 API·식별자·표준 용어는 정확한 형태를 유지한다. 실제 책임·호출·저장 위치·실패 동작을 서술한다. 같은
의미를 반복하거나 임의의 숫자·근거·성과를 넣지 않는다.

이유: 개인 개발·응답 지침과 현재 제공한 작성 지침에 근거한다. 자연스러운 문체를 위해 기술적 의미를 희생하지 않는다.

예외·한계: 코드 주석·docstring·공개 영문 문서는 기존 독자와 문체를 따른다. contract는 API 명세·입출력 조건 등
문맥에 맞게 쓴다. ancestor·common ancestor·merge base도 서로 구분한다.

DOC-004 — 설계 결정의 기록


상태: 명시

적용 범위: 대안 선택·충돌 해결·범위 변경

근거: U08 · U07 · L01
· L02


요구사항, 현재 동작, 가정, 제안, 확정을 구분한다. 선택한 대안과 이유, 제외한 대안의 조건, 검증 근거와 남은 불확실성을 남긴다. 설계와
코드가 달라지면 호출자·DTO·테스트를 확인해 관련 문서를 함께 맞춘다.

이유: 충돌을 확인하거나 둘 중 하나를 선택했을 때 이유와 작업내용을 남기라는 요청에 근거한다.

예외·한계: 작은 수정에 형식적인 ADR을 강제하지 않는다. 해당 결정의 검토에 필요한 기록이면 된다. assistant 제안만 있으면
사용자 확정으로 기록하지 않는다.

WORK-001 — 가장 작은 완결된 변경


상태: 명시

적용 범위: 구현·수정·리뷰

근거: L01 · U10


관련 구현·호출자·테스트·설정을 읽은 뒤 요청을 만족하는 범위까지 완결한다. 무관한 재서식·개명·정리·새 기능을 묶지 않는다. 분석 요청은
구현 요청과 구분한다.

이유: 개인 개발 지침과 현재 문제만 해결하고 후속 기획은 별도로 진행하라는 요청에서 확인했다.

예외·한계: 줄 수가 가장 적은 임시방편을 고르라는 뜻은 아니다. 필요한 계약·문서·회귀 검증까지 포함하되 인접 문제로 범위를 넓히지
않는다.

WORK-002 — 호환성과 기존 데이터


상태: 명시

적용 범위: 공개 API·설정·schema·이벤트·저장 상태

근거: L01 · L02


변경 전 소비자를 확인한다. 공개 이름·기본값·오류 의미·설정 우선순위·저장 형식을 바꿀 때 기존 호출과 데이터에 미치는 영향을 확인한다.
사소한 스타일 변경을 이유로 호환성을 바꾸지 않는다.

이유: 개인 개발 지침은 null·empty·default와 기존 저장 데이터를 명확히 다룬다.

예외·한계: 사용자가 의도적으로 동작 변경을 요청했다면 그 범위의 변경은 가능하다. 불필요한 영구 compatibility layer를
미리 추가하지 않는다.

WORK-003 — 동작을 검증하는 테스트


상태: 명시

적용 범위: 기능·오류·동시성 변경

근거: L01 · L02 · G05


실제 실패와 경계 조건을 재현하는 테스트를 우선한다. 기대값을 검증 대상 구현이나 LLM 출력에서 다시 만들지 않는다. 시간·순서 의존
테스트는 가능한 한 결정적 동기화를 사용한다.

이유: 개인 개발 지침과 최근 검증 가이드에서 반복된다. 성공 경로만으로 구분할 수 없는 실패·취소·오래된 상태를 확인한다.

예외·한계: coverage 숫자만 올리거나 구현을 그대로 복제한 테스트를 추가하지 않는다. 문서 수정은 링크·예제·명령 검증처럼
변경에 맞는 검사를 한다.

WORK-004 — 완료와 검증 범위의 보고


상태: 명시

적용 범위: 커밋·push·release·작업 결과

근거: L01 · L02


실제로 실행한 검사와 결과, 읽기만 한 범위, 미검증 범위를 구분한다. 배포·게시·push는 로컬 명령 성공만으로 최종 외부 상태를 추정하지
말고 해당 결과를 확인한다. 한 커밋은 검토 가능한 일관된 변경을 담는다.

이유: 검증하지 않은 성공을 주장하지 않는 개인 지침을 작업 종료 기준에 적용한다.

예외·한계: 코딩 스타일 적용만으로 commit·push·배포·외부 메시지 권한이 생기지 않는다. 현재 작업에서 요청한 범위에 따른다.

WORK-005 — 마이그레이션 종료 후 임시 호환 코드 정리


상태: 선호

적용 범위: 요청 범위 안에서 완료한 이관 작업

근거: 추가 대화 U31


호출자와 사용처를 새 경로로 옮기고 검증한 뒤 사용하지 않는 shim·호환
module·중복 구현을 제거한다. debug code, 주석 처리한 옛 구현, 임시 TODO를
필요 없이 남기지 않는다.

이유: 구현 후 이전 코드 제거와 안정성 검증을 반복 요청했다.

예외·한계: 외부 소비자가 아직 구 API를 사용하는 호환 기간까지 임의로 단축하지 않는다.
의도적으로 남기는 항목은 이유·종료 조건을 기록한다.

WORK-006 — 설치 결과와 실제 실행 경로 검증


상태: 선호

적용 범위: wheel·npm package·VSIX·release

근거: 추가 대화 U32


개발 checkout의 성공만으로 배포 성공을 판단하지 않는다. 생성 artifact에
필요한 runtime 의존성·prompt·설정이 포함되고 깨끗한 환경에서 로딩되는지
확인한다. 게시가 비동기라면 registry의 최종 공개 상태까지 확인한다.

이유: 개발 workspace에만 있는 dist를 참조한 패키징 문제와 게시 후 조회 검증
기록에서 반복 확인한 기준이다.

예외·한계: 실제 OS·실제 호스트에서 확인하지 않은 검사를 그렇게 보고하지 않는다.
변경 영향이 없는 검증을 매번 반복하거나 모델 호출을 불필요하게 늘리지
않는다. 독립 package는 독립적인 테스트 환경과 테스트 코드를 둔다. 같은
코드를 commit했다는 이유만으로 동일 테스트를 다시 돌리지 않는다.
U35

WORK-007 — commit 메시지의 목적과 형식


상태: 선호

적용 범위: 별도 저장소 규칙이 없는 commit 메시지

근거: 추가 대화 U33


[Type] Base verb ... 제목과 필요할 때 본문 bullet을 사용한다. Type은
Feature, Improve, Fix, Doc, Refactor, Test, Chore 중 선택한다. 제목은
50자 이내, 본문은 300자 이내, bullet은 50자 미만을 목표로 한다. 변경한
내용과 이유를 적고 과거형·문장 끝 마침표를 피한다.

이유: Commit Defender의 생성 prompt에 사용자가 직접 제공한 형식이다.

예외·한계: 당시 제품의 메시지 생성 규칙을 개인 후보 기본으로 확장한 선호다. 기존
Conventional Commits·한국어 규칙은 덮어쓰지 않는다. 원문의 특수문자 금지는
필수 [Type]과 bullet 표기까지 없애는 의미로 해석하지 않는다.

REVIEW-001 — 결함·위험·기존 동작의 구분


상태: 선호

적용 범위: 수동·자동 코드 리뷰 결과

근거: M01


호출자·설정·테스트와 base 동작을 확인한다. 새 변경의 결함, 조건부 위험,
기존부터 있던 동작, 미확인 추측을 구분한다. 자동 리뷰와 비교할 때 원래
번호·범위·겹치는 내용·불일치를 보존한다.

이유: 리뷰 보고서 복구·재작성 과정에서 확인한 사용자 요구와 반복 검증 기준이다.

예외·한계: 일부 파일만 검토한 결과를 전체 승인으로 표현하지 않는다. lint가 처리하는
사소한 서식 문제를 동작 결함과 같은 수준으로 나열하지 않는다.

REVIEW-002 — 심각도 체계와 근거를 함께 표시


상태: 선호

적용 범위: 리뷰 finding·보고서·게시 요약

근거: M01, M02


중요도를 붙일 때 해당 체계의 의미와 영향 조건을 적는다. 외부 자동 리뷰의
P1·P2와 제품 내부 우선순위 또는 Critical·High·Medium을 같은 척도로
단순 치환하지 않는다. 길이 제한이 있으면 finding 단위로 우선순위를 정하고
생략 범위와 전체 보고서 위치를 남긴다.

이유: 심각도 기준을 요구한 사용자 교정과 긴 리뷰 게시의 근거 보존 경험을 반영했다.

예외·한계: 표시 순서와 severity 숫자는 프로젝트마다 다르다. 특정 보고서의 기준을
모든 시스템의 기본값으로 이식하지 않는다.
